YashOS Assistant

A text and voice assistant that tells recruiters about Yash and makes the case for hiring Yash. It is built as its own small project with a test page, then added to YashOS as an app. Its architecture is part of the pitch: small, measured and easy to change.

What it does

Two audiences open it. A recruiter wants quick, specific answers and a way to reach Yash. An engineer wants to see how it was built. Text comes first, because most recruiters are on a phone or in an open office and will type. Voice is one tap away on the Talk button.

Assistant: Hi, I'm Yash's AI assistant. I can tell you about Yash's AI work and time at Amazon, or check the fit for a role you're hiring for.

What has Yash built with AI? What did Yash do at Amazon? Check the fit for my role How were you built?

Fixed text with no model call, so it appears instantly. Each starter is also a test case.

for recruiters

Answers questions about Yash

Experience, projects, skills, education, availability, location and working style. Every answer lists its sources and has a copy button.

for recruiters

Checks the fit for a role

Paste a job description. A one-sentence verdict streams first, then a fit card: each requirement with its evidence and source. Weaker matches say "Closest:", and missing requirements are never listed. Voice reads only the verdict and top two rows.

for recruiters

Hands over to Yash with context

Messages opens with a draft note naming the role and what was discussed. A template writes it, not the model, and it is never sent automatically. Contact details never pass through the AI.

in YashOS

Shows it on screen

While talking about Amazon, it offers a chip that opens the Time Machine at Amazon. Projects open the project, and the resume is one tap.

for engineers

Says how it was built

"How were you built?" gets an open answer. Under the hood shows each answer's timings, model, tokens, cost and sources, and links the public repo.

for Yash

Learns what's missing

Questions it answered with partial or no coverage are stored, as asked, in a D1 table gaps for 30 days, and npm run gaps lists them. Each answer Yash adds becomes a new test, so the assistant improves without slipping back.

How it fits together

Everything runs in one Cloudflare Worker, served from the portfolio's own address. The Worker is a thin front door. Each conversation lives in its own Durable Object: a small server-side object with its own SQLite storage, found by name. The client sends only the new message.

Why it is no longer stateless. Revision 3 kept the conversation in the browser so the Worker held nothing. That took three workarounds: signed history, which could still be spliced or replayed; voice counters per socket, which reset on reconnect; and a hop back through the browser at the end of every spoken turn (80 to 150 ms on Indian mobile networks). Exact limits need state anyway. One object per conversation removes all three: less code and fewer ways to attack it.
POST /session

Runs when the app opens: an invisible Turnstile check and a per-IP rate limit. It creates the conversation under a random id and returns a short-lived token, the PROTOCOL_VERSION and the mode: voice, text only or resting.

POST /chat

One text turn, handed to the conversation's object, which streams back text, refs and events as SSE (server-sent events: one HTTP response that stays open and delivers events as they happen).

WS /voice

Audio up; events and audio down. The token is checked before the upgrade, in the Sec-WebSocket-Protocol header, and the Worker answers with a fixed protocol name, so no secret ends up in a URL or a log.

same origin

A Cloudflare route sends yashos.dev/assistant/* to this Worker, ahead of the portfolio's custom domain. No cross-origin checks, and the existing Turnstile setup works as it is.

One voice turn

  1. The visitor taps Talk. The client streams 80 ms frames of 16 kHz audio over /voice, and the conversation's object relays them to Flux.
  2. Flux sends live words for the captions and decides when the visitor has finished, so there is no silence detector to build or tune. Names from the knowledge bundle are given to it as key terms at build time.
  3. At turn end the object builds the prompt and streams from the model straight away. It opens the voice socket at the same moment, so the voice is ready when the first clause of six or more words is.
  4. Each sentence that passes the output gate goes to the voice as its own message; when its audio ends with a message marked final, the next one goes. Synthesis is faster than playback, so there is no audible gap. Text and audio share a sentence id, so captions match the voice.
  5. While the assistant speaks, the mic sends silence. After playback, the mic stays open about 8 seconds for a follow-up, then closes until tapped.

Half-duplex: one side talks at a time

Audio in the browser

One AudioContext at the device's rate, created on the Talk tap since browsers start audio only after a tap. An AudioWorklet (a small audio script from the same site) downsamples to 16 kHz in 80 ms frames. The mic asks for echoCancellation: "all" on Chromium, true elsewhere; 300 ms of trailing audio follows a push-to-talk release.

The relay

The object pumps frames to Flux in its own code rather than passing the socket through, so it can count audio from bytes (32,000 is one second) and refuse audio faster than real time. It sets binaryType = "arraybuffer" before accepting. Deploys and hidden iPhone tabs drop sockets, so the client reconnects.

Swappable parts

The core never talks to a vendor directly. Three outside services sit behind ports: small interfaces, each with a real adapter and a scripted fake. The fakes run the tests and a demo mode that needs no keys, switched on only by an explicit ASSISTANT_DEMO=1. Two more contracts are ours and fixed: the event protocol every surface reads, and the knowledge bundle.

CI typechecks the client with DOM types and the worker with Workers types. YashOS binds only to AssistantSession. A client on an older major PROTOCOL_VERSION shows "reload to update"; minor changes only add fields. How YashOS installs the client is decided at integration.

The brain

The prompt is built in layers, with the parts that never change first. MiniMax caches a stable prefix of 512 tokens or more automatically and reads it back at a tenth of the price. How long the cache lasts isn't documented, so Phase 0 measures it; warming it at /session stays only if that matters.

Why no retrieval (RAG)

RAG means searching the knowledge for a few relevant pieces and putting only those into the prompt. This decision record explains why the whole bundle goes in instead.

QuestionAnswer
How big is it?About 20K tokens; lib/content is 19 KB today. CI prints the count on every build.
What does it cost?About $0.0003 a turn: 20K cached tokens at Flash's $0.015 per million.
Is that normal?Anthropic's guidance: a knowledge base under about 200K tokens can go into the prompt whole.
What would RAG add?Four new ways to fail: missed searches, facts split across chunks, wrong ranking, and an index that drifts from the content.
When does this change?CI fails at 60K tokens; then search goes inside one function. CI also checks every section id is targeted by a test case.

One call per answer

The model answers in plain prose and ends with one line of data. The Worker streams the prose, holds the data line back, checks it against the schema and turns it into refs and actions. A broken data line is ignored, and the answer still works.

Choosing the model by numbers

Written before the test: voice uses the cheapest candidate with a p50 of 700 ms or less to the first answer word, measured from India and the US, that passes the safety probe. Candidates: MiniMax-M3.1-Flash at effort low (it always reasons, and defaults to the slowest effort), MiniMax-M3 with thinking off (same key and adapter), and Claude Haiku 5.5 with thinking off if there is a key.

Measured on 8 November (30 runs each, from a laptop in India): Flash 1.59 s p50 to the first answer word, M3 1.63 s. No candidate met 700 ms, and M3 with thinking off failed the safety probe (it answered "Yes." about a skill the knowledge doesn't have, and invented a growth area). Text stays on Flash, and its data terms are accepted (see Safety). Measured on staging, 11 November (Cloudflare's network, server-side timings): text reaches its first answer word in 2.0 s p50 and 3.3 s p90, slower than from the laptop, and almost all of it is MiniMax's own wait before Flash starts reasoning; voice took 2.5 to 4.0 s from the end of a question to the first sound (three recorded questions). The 1-second text and 1.5-second voice targets are not reachable on Flash; the voice model stays open. Details: docs/decisions/0001-phase-0-results.md.

A provider-neutral model port

stream({stable, turns, tail, effort, maxTokens}, signal) yields text, a content-free "still thinking" tick, and usage. Reasoning never leaves the adapter; a test proves only final text crosses the wire. History stores neutral turns, so changing provider breaks nothing.

Knowledge flows one way

Facts come from YashOS's lib/content: today npm run knowledge:sync copies them into knowledge/content.json; after integration a daily workflow pulls the site's published /assistant-content.json and opens a PR when it changes. Stories and policies are markdown Yash writes; an unknown ref fails the build.

Cancelling for real

When the visitor stops playback or leaves, the object aborts the model stream and closes the voice socket, so an interrupted reply stops costing money. Phase 0 checks that both providers really stop.

Built to grow

Three things will change: how much there is to know about Yash, what the assistant can do on screen, and which models run it. Each one has a planned path that leaves the rest of the system alone.

How knowledge reaches the model

Today every section goes into the cached part of the prompt. There is no search step, so nothing can be missed, and MiniMax reads cached tokens back at a tenth of the price. That stays right until the knowledge passes about 25K tokens or answers measurably slow down. After that, a search step picks a few sections for each question. A lookup tool, where the model asks for a section by name, is a third option for text only, because each lookup adds a round trip that voice can't afford. All three hand the model the same sections under the same typed refs, so nothing that checks answers has to change.

Adding a feature

A new feature is mostly one declaration and one test, not a new pipeline. On-screen control by voice, such as "show me the Amazon work", goes through the data line. It arrives while the first sentence is still being spoken, so the window opens during the reply, not after it.

What stays fixed on purpose

  • Every visitor word is data, wrapped in a per-request boundary, in every mode.
  • The output gate and the grounding check run on every answer, in both modes, inside the brain.
  • The model names things (refs and actions). It never names YashOS windows, URLs or contact details.
  • Voice makes one model call per answer until a measurement shows a tool call fits.
  • The assistant's behaviour doesn't change without an eval run.

Changing any of these needs a written decision record in docs/decisions.

How it talks

It speaks about Yash in the third person, using the pronouns Yash chooses, and says it is an AI in the greeting. It is warm, brief and specific: numbers and outcomes, not adjectives. Spoken answers are one to three sentences, then it offers more.

Point to the closest evidence, then be plain

It never volunteers a weakness and never says Yash "lacks" something. Asked about something outside its knowledge, it first gives the closest real evidence and says so. Pressed again, it says plainly that this isn't in what it knows about Yash's work and offers Yash directly. It never states or implies a skill, title, number or employer that isn't in the knowledge base; a redirect that sounds like a yes counts as an invented claim, and the tests check for it. The pressed-twice wording was approved as written on 11 November.

Visitor: Has Yash worked with Kubernetes?

Not really, that's a gap in Yash's experience.

Yes, Yash has deep Kubernetes experience.

Assistant: The closest in Yash's work is running production services at Amazon, with the CI pipelines, telemetry and on-call rotations that kept them dependable.

Visitor: But Kubernetes specifically?

Assistant: That isn't in what I know about Yash's work, so I won't guess. Yash can answer that directly. Want me to open Messages with a note?

Visitor: What did Yash work on at Google?

Assistant: Yash hasn't worked at Google. Yash's roles have been at Magenta Connect, Techsquad, Amazon and UAlberta. Want to start with the AI work at Magenta?

False premises (a wrong employer, an inflated title, an invented number) are corrected by stating the record.

Honest, not pushy

  • Only facts from the knowledge base, with sources for every answer.
  • "How were you built?" and "what model are you?" are answered openly, pointing to Under the hood and the public repo.
  • "What is Yash bad at?" gets Yash's own growth-area answer.
  • At most one unasked-for Messages offer per conversation, and a follow-up question at most every other answer.
  • Hype words are caught in code by the output gate.

Within bounds

  • Never speaks as Yash, commits to nothing on Yash's behalf, and gives no ratings or opinions about companies or people.
  • Off-topic requests get one friendly line and a redirect.
  • Age, religion, family or health: politely declined as not relevant to hiring.
  • Pasted text is data, never instructions.
  • English replies in v1.

Flow

  • Opening: the fixed greeting and four starter questions.
  • Recruiter spotted: asks once about the role, then tailors everything to it.
  • Pitch: claim, evidence, why it matters for their role.
  • Pushback ("isn't that junior for this?"): reframes with scope and ownership.
  • Close: the resume, or Messages with a draft note.

Safety, limits and cost control

Limits in units, not dollars

Per session, exact, in the object: turns, audio seconds measured from bytes, and spoken characters. Per day, for everyone, in D1, each one atomic UPDATE … RETURNING with no rollover: 400 model turns; 1,800 s of voice listening, reserved 15 s at a time and the unused part refunded when the socket closes; and 60,000 spoken characters, with at most 500 spoken per reply. Each visitor also has 600 s of listening a day, reserved together with the shared blocks and refunded the same way, so one visitor can't use up the day's allowance. The rest of a reply is shown as text only, marked spoken: false. When a voice ceiling is reached, or a visitor's own 600 s, voice rests (for that visitor, in the second case): the socket gets voice_resting and the assistant carries on in text. When the turn ceiling is reached, the assistant rests: a static card with no AI (pitch, resume, Messages), and Yash is alerted. A ceiling var set to an invalid value counts as 0, so a typo fails closed. Voice is the default mode; ASSISTANT_MODE=voice|text|off is the kill switch.

The hard cap and the threat model

MiniMax runs on a prepaid balance with auto-recharge off, so that balance is the hard cap. Flux is billed afterwards by Cloudflare, so the daily voice ceiling covers it. The bot-check rate limit runs only at /session, in its own namespace. A per-visitor cap of 60 model turns per IP per day runs on every turn, and one of 600 s of listening per IP per day runs on every audio block. Their D1 rows are keyed by an HMAC of the day and the IP, so no raw IP is stored, and the rows are deleted once their day ends. The voice socket closes when the session expires, and empty or misaligned audio frames are refused and don't keep a socket alive. Scripts and freeloaders are stopped; a funded attacker can cost at most one day's ceilings per day.

Guards in code, not a moderation model

Input: messages capped at 4,000 characters (12,000 for a job description), invisible Unicode stripped, pasted text wrapped in a per-request boundary marker. Output, per sentence, before it is shown or spoken: no URLs, emails, phone numbers, code, profanity, over-length, or ten-plus words copied from the visitor; each is checked on the sentence before and after markdown is stripped, so formatting can't smuggle a link through. Markdown is stripped, hype words are flagged, and a stray "he" or "she" is rewritten to "Yash". A moderation model comes in only if a harmful reply gets past.

Data kept small

Visitor input is not redacted. The output gate still blocks emails and phone numbers in answers. A pasted job description is logged as a hash and length; visitor text never reaches console logs, and turn-log rows hold no visitor words. One table is the exception: questions answered with partial or no coverage are stored, as asked, in the D1 table gaps for 30 days, and npm run gaps lists them. Conversations live in each conversation's Durable Object for 30 days and can't be listed. The disclosure (src/client/disclosure.ts) names each processor. Flux on Workers AI keeps no data. MiniMax may use inputs to improve its services, with no opt-out; the owner accepted that on 11 November 2026 and the disclosure says so.

No bypass paths

The hourly check is an in-Worker Cron Trigger that mints its own token, and a scheduled GitHub Action probes the public route from outside. Staging uses Turnstile test keys. Fakes are chosen at deploy time, never per request. Demo mode needs an explicit ASSISTANT_DEMO=1. A missing model key in production is a configuration error that /assistant/health reports, not a silent demo. The prompt and knowledge are written as if public, because the repo is public on GitHub.

Watching it and undoing it

Each turn writes one TurnRecord (timings, tokens, model, prompt and knowledge hashes, grounding result) that the inspector, report and scorecard all read. Alerts go by email from the Worker through Cloudflare's send_email binding to a verified address held in a secret. There are four kinds: canary failed, canary slow (over 10 s), resting, and misconfigured. Each kind sends at most one email a day. The hourly canary skips, and doesn't fail, when the day is already resting. Voice falls back to text, and the model gets one retry, then a message that opens Messages. One wrangler rollback restores code, prompt and knowledge together.

Quality tests

An AI system can't be trusted on vibes. The test suite is written before the brain and runs against /chat exactly as visitors use it. Risk decides what blocks a change.

Grounding check

Every number, date, employer, title, degree and project name in an answer must appear in the sections it cites. It sorts what it finds: invented (in no section and not in the visitor's own words, which fails a safety test) and uncited (true, but from a section the answer didn't cite, which is reported). It runs in CI and after every live reply, never blocking one; on the first 107 real answers, sorting this way cut the flag rate from 44 answers to 5, all genuine.

A judge that is itself tested

15 good answers and 15 copies with one planted defect each (an invented skill, a wrong number, an implied yes, a citation that doesn't fit). Trusted at 95% caught and 2% false flags. Fake models test the harness too: inventing or empty fakes must fail.

Results kept, CI kept safe

Each run is committed as a file keyed by git sha, prompt, knowledge, model and judge versions. Tests run on pull requests (forks get no secrets), pushes to main and by hand, never pull_request_target, on a staging key with its own small balance.

Voice gets its own weekly browser test: recorded questions in Indian- and US-accented English are played as the microphone, and the transcript, answer and timing are checked.

In YashOS

Text goes into YashOS before voice, in Phase 2, following portfolio-os conventions: modern and retro versions, content from lib/content, and npm run check passing. It is a normal app in lib/apps.ts, so the dock, search, a retro twin, the phone sheet and intents come free.

The client now exists. AssistantSession (src/client/assistant-session.ts) is a framework-free object that holds the session, the conversation as an immutable snapshot, and voice. useAssistant (src/client/react.ts) is the React binding, and the playground runs on both. How portfolio-os installs the client is still decided at integration.

Modern and retro

Modern: a text-first panel with a Talk button, an orb that shows the Talk state, captions and source chips. Retro: an XP-style window with balloon captions. "Under the hood" is one inspector styled by the theme. The speaker follows the saved YashOS sound setting.

Ways in

Dock, search ("Ask about Yash…" sends the typed text in), the terminal (ask <question>), and a deep link: ?ask or ?ask=fit, fixed values only, never free text. It is read outside the dev-only guard and routed through the intent system. The Hero, welcome note and phone notice point to it.

Refs become effects

A small lib/assistant/effects.ts maps refs to existing effects: roles open experience, projects work, skills toolkit, and doc:resume uses openResume(). Each appears as a chip. Only desktop voice mode opens the window by itself; on a phone it would cover the chat.

Hand-over to Messages

pick('hiring') plus a new prefill(text) draft, within the 2,000-character limit, never sent automatically. A client template writes the note (the role and titles of sources discussed), with an optional short id that grants nothing. The disclosure says the visitor's questions are shared with Yash.

Costs YashOS nothing

No bytes load until the assistant opens, and the client stays under 30 KB gzipped. Turnstile runs invisibly as the app opens, so the first answer doesn't wait for it. The mic is requested only on Talk.

Accessible

Captions always visible, answers announced to screen readers, Space to talk and Escape to stop, a still orb with reduced motion, and push-to-talk on phones.

Review findings

First review. Before revision 3, an independent reviewer read the design and the YashOS code and checked risky claims against vendor docs. It agreed with one text brain behind the voice, the whole knowledge base in the prompt, and a model that can't act. Its fixes that still stand: the same-origin route, real cancellation, an hourly check, one-command rollback, a judge from another vendor and Messages as the only contact path.

Second review

Six reviewers, each with one lens (recruiter, AI hiring signal, real-time voice, evolvability, simplicity and risk, security, cost and privacy), proposed 43 changes. Two sceptics judged each one for value against complexity and for correctness against vendor docs. These are the adopted outcomes.

Third review

On 10 November an independent reviewer read the built code. These are the findings and what changed.

FindingWhat changed
Voice spend had no daily ceiling of its own.Daily ceilings in D1: 1,800 s of listening, reserved 15 s at a time, and 60,000 spoken characters, at most 500 per reply. Past a ceiling, voice rests and text carries on. Voice is on by default, so these are what cap its cost. An invalid ceiling var counts as 0.
One visitor could use the whole day's turns.A cap of 60 model turns per IP per day, and 600 s of voice listening per IP per day, charged with each 15 s block of the shared allowance. Each is keyed by an HMAC of the day and the IP (the voice one with its unit). No raw IP is stored, and the rows are deleted when their day ends.
A missing model key could turn into a silent demo. Nobody would be told.Demo mode needs ASSISTANT_DEMO=1. In production a missing key is a configuration error shown by /assistant/health. Alerts go by email: canary failed, canary slow, resting, misconfigured.
The output gate and sentence splitter had gaps.Four fixes. A phone number split across sentences ("416. 555. 1234") is joined and blocked. A literal <meta> in prose no longer cuts the answer short. An empty reply shows a fallback sentence. The copied-text rule checks every visitor turn, not just the latest. And visitor text is normalised and stripped of format characters, so a soft hyphen or fullwidth underscore can't forge the closing boundary tag.
The knowledge itself was never run through the gate.knowledge:check fails if any knowledge sentence would be blocked.
Each host page would have to rebuild the client logic.One object, AssistantSession, with a React binding on top.

Considered and rejected

  • Analytics Engine, Workers Logs and object alarms instead of D1: three parts for one, a retention that breaks the 30-day deletion promise, and the report still needs a listable store.
  • AI Gateway in v1: an extra hop and credential, and exact-match caching is useless for chat. Revisit for a log viewer or spend caps.
  • A signed history chain: moot once the object owns the history.
  • MiniMax's bidirectional voice socket: it turns raw model text into sentences on the server, which we can't use because sentences must pass the gate first, and its sentence events carry no ids or text. Phase 0 times both sockets anyway.
  • Citation markers per sentence, for now: format risk on a model that ignores stop sequences; answer-level refs and the grounding check get most of the value.
  • Follow-up chips, a "share" reply style, context from the front window, and recall-by-position analysis: put off until logs or suite size justify them.
